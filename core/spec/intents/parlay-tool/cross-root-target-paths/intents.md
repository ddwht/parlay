# Cross-root target paths

> The deep buildfile validator resolves every plan and cross-cutting path against a single source root derived from the buildfile's own location, so a feature can never reference a file that lives in a different root — most concretely, a parent-root file like the repo-level `CLAUDE.md` from a child-root feature's buildfile. `planRootDirFromBuildfilePath` returns exactly one root; `plan.modifies` / `target-files:` paths are joined against it and checked for on-disk presence there. A child-root feature whose cross-cutting concern genuinely touches a parent-root file has no representable way to say so: the path resolves under the child root, isn't found, and fails with `plan-modify-target-missing`. This is distinct from `parlay-tool/cross-cutting-target-paths`, which routes `target-files:` to `plan.creates` vs `plan.modifies` and relaxes existence via same-root sibling creates — all still within one root. This feature lets a buildfile reference a file in another (typically the parent) root.

---

## A buildfile plan/cross-cutting entry can reference a file in another root

**Goal**: Let a child-root feature's buildfile name a target file that lives outside the child root — chiefly a parent-root file such as the repo-level `CLAUDE.md` or a shared parent-level config — and have the deep validator resolve and check that path against the correct root instead of failing it as missing under the child root.
**Persona**: Parlay tool maintainer
**Priority**: P2
**Context**: `planRootDirFromBuildfilePath` in `core/internal/agent/validate_project.go` (around line 690) walks up from the buildfile to `<root>/.parlay/build/` and returns that single `<root>`. `validatePlanSection` joins every `plan.modifies` / `plan.creates` / cross-cutting `target-files:` path against that one root and runs its on-disk checks there (`plan-modify-target-missing`, `plan-create-collision`, and the cross-cutting routing rules). There is no way for an entry to opt into a different root's namespace. In this multi-root repo, parent-level artifacts (the repo-level `CLAUDE.md`, shared parent configuration, the agent surface) live only at the parent root; a child feature (`studio`, `core`) whose cross-cutting concern legitimately modifies one of them cannot express it — the path resolves under the child root, is not found on disk, and the entry is rejected. The `parlay-tool/cross-cutting-target-paths` feature (already done) governs which plan section a `target-files:` path routes to and lets `plan.modifies` be satisfied by a same-pass sibling `plan.creates`, but every path there is still resolved against the one derived root; cross-root reach is orthogonal to it.
**Action**: Introduce a representable way to mark a plan/cross-cutting target as belonging to a different root and resolve it there. Candidate shapes (pick in dialogs): an explicit root-qualified path (a `@<root>/` prefix or a `root:` field on the entry), a top-level scope hint on the buildfile declaring which foreign roots it may reach, or a "loose-target" annotation that resolves against the parent root's namespace. The validator resolves such an entry against the named root — validating parent-pointer integrity through the multi-root config, not an arbitrary filesystem path — and applies the same on-disk and routing checks it applies within-root today. Resolution is deterministic and driven by the registered-root topology, not a bare path walk.
**Objects**: cross-root-target, parent-root, plan-modify-target, cross-cutting-target-files, plan-root-dir, registered-root-topology, root-qualified-path

**Constraints**:
- Cross-root reach is explicit and opt-in per entry (or per buildfile) — a bare relative path continues to resolve against the buildfile's own derived root exactly as today; nothing about the single-root common case changes.
- A referenced foreign root must be a registered root reachable through the multi-root config (parent pointer validated), not an arbitrary absolute or `../`-relative filesystem path — resolution goes through the same root machinery every other command uses, not a bespoke path escape hatch.
- The child→parent direction is the primary case (a child feature reaching a parent-root file); whether sibling-child→sibling-child reach is permitted is decided in dialogs, but if disallowed it fails with a clear code rather than resolving to the wrong place.
- On-disk and routing checks for a cross-root target run against the foreign root: a modifies-target must exist under that root, a create-collision is checked there, and the cross-cutting `target-files:`/`target-creates:` routing rules apply unchanged.
- Error messages name the resolved root explicitly, so an author who mis-qualifies a path sees which root the tool looked in — not a bare "missing in source root" that hides the root mismatch.

**Verify**:
- A child-root feature's buildfile that references the repo-level (parent-root) `CLAUDE.md` as a cross-cutting `target-files:` modify target validates cleanly when the file exists at the parent root, where today it fails with `plan-modify-target-missing` under the child root.
- The same reference with the file genuinely absent at the parent root fails with a missing-target error whose message names the parent root that was searched.
- A bare relative path in a child-root buildfile still resolves against the child root and behaves byte-identically to today (no regression for the single-root case).
- A cross-root reference naming a root that is not a registered, reachable root fails with a clear code rather than resolving against the buildfile's own root or an arbitrary filesystem location.
