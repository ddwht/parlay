# Schema Versioning House Rule

This is a cross-cutting policy doc, not a file schema — it does not describe an on-disk artifact of its own. It states the one rule every **evolvable, structurally-versioned** parlay artifact follows, so a reader who has learned it from one schema (`domain-model.schema.md`, below) does not have to re-derive it from scratch for the next one.

## The rule

An artifact that carries a `schema_version:` field declares it:

- **snake_case**, always — `schema_version`, never `schemaVersion`, `schemaversion`, or `version`.
- **a plain integer**, always — never a semver string (`"1.2.0"`), never a date, never a string tag.
- **monotonically increasing**, starting at `1` for the artifact's first released shape.

Not every artifact needs a `schema_version:` field. It's required for artifacts whose on-disk shape is expected to evolve across releases in a way consumers must detect (hand-authored or long-lived generated files). It's optional for artifacts whose shape is pinned by something else already — `adapter-set.schema.md` and `coverage-review.schema.md`, for example, have no version field of their own because their shape is tied to the project's adapter-set topology and the buildfile/testcases hashes they gate, respectively, not to an independent evolution timeline.

## Migrator-or-regenerate: pick one, document it

Every schema that declares `schema_version:` states, in its own doc, which of two policies governs a file at an older version than the running binary expects:

- **Migrator chain** — the artifact is hand-authored, long-lived, or otherwise expensive to reproduce from scratch. Older versions are routed through a registered per-version, in-memory migrator (`v1 → v2 → ... → binary`) that transforms the parsed structure without touching the disk file until the caller explicitly saves. `domain-model.schema.md`'s "Versioning policy" section is the canonical worked example: `agent.RegisterDomainModelMigrator` per version, `schema-version-unreachable` when no migrator chain reaches the binary's version, `schema-version-newer-than-binary` when the file is ahead of the binary (fix: `parlay upgrade`).
- **Regenerate** — the artifact is fully tool-generated from an upstream source that's cheap to re-run. An older version is simply an instruction to regenerate (e.g., `.parlay/build/<feature>/buildfile.yaml` via `parlay build-feature`) rather than something to migrate in place. There is no migrator chain because there is nothing worth preserving in the old file that the regeneration step can't reconstruct from its own inputs.

A schema declaring `schema_version:` with neither policy documented is incomplete — pick the one that matches the artifact's authorship model (hand-authored → migrator; tool-generated → regenerate) and say so explicitly, the way `domain-model.schema.md` and `buildfile.schema.md` do.

## Per-feature blessing instants

`save-build-state` was first designed for whole-project codegen runs: one atomic world-snapshot in which every feature's baseline and the project's code-hashes all moved to a single instant together. That "one-instant invariant" is right for a full run — everything was regenerated, so everything is blessed at once — but wrong for a partial one. `parlay refine` regenerates a handful of files; a save that re-derived *every* feature's baseline from current source would re-bless features nobody rebuilt, clearing their real "this source drifted, the code is behind" signal. A false "stable" verdict is worse than churn.

So the invariant is **relaxed to per-feature instants, not abandoned**. Under `--partial`, `save-build-state` advances the baseline only for the features whose files this run emitted (resolved from the `--emitted` manifest through each file's generation marker); every other feature keeps the baseline — and the `generated-at` instant — it already had, so its dirty flags survive. A full (non-`--partial`) save still blesses every feature together, the original semantics. The project baseline records which features a save blessed in its `emitted:` list, for audit.

The per-feature reads all consumers make are already independent — `parlay diff @feature`, `check-drift`, and `verify-generated` each load one feature's `.baseline.yaml`/`.code-hashes.yaml` and compare against current sources, assuming nothing about a shared instant across features. The one genuinely project-wide instant is the merged buildfile-section hashes in `.parlay/build/_project/.baseline.yaml`: each hash concatenates one section (`models`, `routes`, `fixtures`) across *every* feature, plus a `blueprint` hash covering a cross-cutting artifact no single feature owns. Because that merge mixes emitted and un-emitted content into a single hash per section, a partial run cannot advance only the part it regenerated — and recomputing the whole thing would fold an un-emitted feature's re-planned buildfile, or a changed blueprint, into the blessed hash and clear project-level drift the run never addressed (a false-stable at the aggregate grain). So under `--partial` the stored merged sections are **carried forward verbatim**; only a full world-snapshot save advances them. The tradeoff is deliberate and in the safe direction: after a partial save, `parlay diff` at the project level may report a section still `changed` (a conservative false-*dirty*) until the next full save, while `parlay diff @feature` reports the emitted feature clean from its own per-feature baseline.

## The one historical violation this rule closes

Before this doc existed, `layout.schema.md` declared its version field as `schemaVersion` (camelCase) — the one artifact out of step with every other versioned schema. That field is renamed to `schema_version` as part of this consolidation, with **no dual-key acceptance window**: the layout feature is new enough (v1, freshly landed) that there's no installed base of hand-authored layouts worth bridging with a transition period. The rename is a hard cutover — parser, validator, and every test fixture were updated in the same change. A schema with a real installed base making this same kind of rename in the future should not assume a hard cutover is always acceptable; that call depends on how expensive it is for existing files to update, which is exactly the kind of judgment the "current artifacts and their policy" table above exists to make explicit per artifact.
