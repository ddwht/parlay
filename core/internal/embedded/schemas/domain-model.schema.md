# Domain Model Schema (`domain-model.yaml`)

<!-- parlay-scope: project -->
<!-- parlay-section: cross-cutting -->
<!-- Source: studio-support/domain-model-yaml-migration / cross-cutting/domain-model-schema-artifact -->

The canonical, versioned YAML form of a parlay project's domain model.
Lives at `<activeRoot>/domain-model.yaml` — exactly one canonical model
per active root, never per-feature. Edited by hand, regenerated by
`parlay create-domain-model`, and consumed by every read path
(`parlay create-domain-model`, `parlay load-domain-model`,
`parlay build-feature`, `parlay generate-code`, `parlay migrate-domain-model`).

Hand-editing is a first-class flow. The on-disk YAML is the live source;
re-running `parlay create-domain-model` regenerates it from feature
intents. Both flows produce structurally identical files.

## Open-question resolution (this release)

This document captures the safe defaults selected at the code-generation
phase of `studio-support/domain-model-yaml-migration`:

- **`enum-tone-vocabulary` → `closed-set`** — the `tone` field on a
  `DomainEnumValue` is one of `{neutral, info, warning, danger, success}`,
  matching the adapter's color-token tone vocabulary. Unknown tones fail
  deep validation. Adding a new tone primitive requires a `schema_version`
  bump and a per-version migrator entry; nothing else changes.
- **`entity-field-shape` → `flat-only`** — entity fields are limited to
  the closed type set below. Inline object literals (nested struct-shaped
  fields) are rejected by deep validation; the actionable fix is to lift
  the nested shape into a separate entity joined by a `ref`-typed field.

Changing either decision is a `schema_version` bump.

## Top-level shape

```yaml
schema_version: 1     # required integer; first released value is 1
enums:        []      # optional list of DomainEnum
entities:     []      # optional list of DomainEntity
relationships: []     # optional list of DomainRelationship
operations:   []      # optional list of DomainOperation
```

`schema_version` is **required** and **must be an integer**. Never
semver, never a string tag. Missing it fails parse with code
`missing-schema-version`. Newer-than-binary fails with
`schema-version-newer-than-binary` (run `parlay upgrade`).
Older-than-binary is routed in-memory through the per-version migrator
chain (`v1 → v2 → ... → binary`); the on-disk file is unchanged.
Unreachably-old (no migrator chain reaches binary) fails with
`schema-version-unreachable`.

## `DomainEnum`

```yaml
name: OrderStatus
values:
  - value: pending
    label: Pending          # optional, presentation
    tone: warning           # optional; closed set: neutral|info|warning|danger|success
```

- `name` (required) — referenced from entity field types via the
  `enum:` key on a `DomainField`.
- `values[].value` (required) — raw enum value (e.g. `paid`).
- `values[].label` (optional) — human-readable label.
- `values[].tone` (optional) — semantic tone for rendering. Closed set
  per the `enum-tone-vocabulary` decision; unknown tones fail with
  `enum-tone-outside-closed-set`. Adding a tone is a `schema_version`
  bump.

Presentation metadata (`label`, `tone`) lives on enums deliberately, as
an exception to the "domain is logic-only" rule, so designers can
preview rendering without an adapter round-trip.

## `DomainEntity`

```yaml
name: Order
fields:
  - name: id
    type: uuid
    required: true
  - name: status
    type: OrderStatus       # named-enum reference
    enum: OrderStatus
    required: true
  - name: customer_id
    type: ref
    target: Customer
    required: true
```

- `name` (required) — entity name; referenced by relationship endpoints
  and `ref`-typed fields.
- `fields` (required, may be empty) — list of `DomainField`.

## `DomainField`

```yaml
name: status
type: <closed-set>          # see below
target: Customer            # only when type=ref
enum: OrderStatus           # only when type names an enum
required: true
```

**Closed field-type set** (per the `entity-field-shape` decision):

| `type:`        | Notes                                                  |
| -------------- | ------------------------------------------------------ |
| `uuid`         | UUID v4 string                                         |
| `string`       | Free text                                              |
| `int`          | Signed integer                                         |
| `float`        | Floating-point number                                  |
| `bool`         | True/false                                             |
| `datetime`     | RFC 3339 timestamp                                     |
| `ref`          | Foreign-key reference; **must** also set `target:`     |
| `<enum-name>`  | Names a declared `DomainEnum`; **must** also set `enum:` |

Anything else fails deep validation with code
`field-type-outside-closed-set`. Inline object literals (nested
struct-shaped fields) are rejected with the same code; lift the nested
shape into a separate entity joined by a `ref`-typed field.

## `DomainRelationship`

```yaml
name: customer-orders
from: Customer
to: Order
cardinality: one-to-many
```

- `from` and `to` must resolve to declared entities. Endpoints that
  reference an undeclared entity fail with `undeclared-entity-reference`.
- `cardinality` is drawn from the closed set
  `{one-to-one, one-to-many, many-to-one, many-to-many}`. Unknown values
  fail with `relationship-cardinality-unknown`.

## `DomainOperation`

```yaml
name: cancel-order
input:
  - Order.id              # field names from involved entities
effects:
  - "set Order.status to cancelled"   # free-text declarative statement
```

- `input` is a list of dotted field names from involved entities
  (e.g. `Order.id`, `Customer.email`). Each name is resolved by deep
  validation to an existing field on a declared entity; unresolved names
  fail with `operation-input-field-not-found`.
- `effects` is a list of declarative free-text statements describing the
  operation's domain consequences. The schema does **no** syntactic
  check on them.

## Read-path precedence

Every domain-model consumer routes through the CLI's standard domain-model
loader, which consults only `<activeRoot>/domain-model.yaml`. The legacy
`domain-model.md` (when present, as a pre-migration artifact) is never
parsed, never merged, never consulted as a fallback. A project with
both `.md` and `.yaml` has the YAML as the sole live source.

## Versioning policy

- `schema_version` is a **monotonically increasing integer**. The first
  released value is `1`.
- Adding a primitive (a new field type, a new tone, a new cardinality)
  requires a `schema_version` bump and a per-version migrator entry
  registered in `agent.RegisterDomainModelMigrator`. No code outside
  the schema and the migrator changes for the type system itself.
- Migrators are pure functions over the in-memory model; they do not
  write to disk, do not consult the network, and do not require AI
  inference.
- Newer-than-binary YAML refuses to load with an actionable error
  pointing at `parlay upgrade`.

## Deprecated: `operations:` field

<!-- parlay-extends: parlay-tool/multi-adapter/domain-model-operations-deprecation -->

The top-level `operations:` field is **deprecated** in favor of per-feature `spec/intents/<feature>/capabilities.yaml`. The new artifact carries the full closed-vocabulary contract (`kind`, `subject`, `input`, `output`, `errors`, `policies`, `steps`); the legacy `operations:` field cannot express most of those terms.

| Mode | Severity |
|---|---|
| authoring (`parlay validate`) | warning |
| build (`parlay build-feature`, `parlay generate-code`) | error |

Validation surfaces `domain-operations-deprecated` whenever `operations:` is non-empty. `parlay build-feature` stops consuming the field for routing or codegen; the value is preserved in the file but ignored.

### Migration

`parlay migrate-domain-operations` walks each entry under `operations:`, asks the designer which feature owns it, and writes a stub with `kind: unknown` into the chosen feature's `capabilities.yaml`. After the migration, the designer fills in the real `kind:` (`command` or `query`) and the rest of the operation shape. The `kind: unknown` stub fails the build-mode `capabilities-stub-unfilled` rule until that's done.

The migration command does not delete the deprecated field automatically. The designer reviews the per-entry migration outcomes and clears the field manually once the new capabilities are correct.
